# Research: 求人・求職の掲示板（Axis ボード）

**Date**: 2026-10-04 | **Plan**: [plan.md](./plan.md) | **Spec**: [spec.md](./spec.md)

前提：001 の技術構成（Next.js 16 + TypeScript の単一アプリ、PostgreSQL 17 + Prisma 7、Better Auth、
本番 AWS ECS Fargate + RDS、ローカル Docker Compose、AI は OpenRouter／Bedrock）を引き継ぐ。
001 の research.md（R1〜R11）で決めたことは、ここで変えるものを除いてそのまま有効とする。

---

## R1. 認証：メールアドレス＋パスワードのみに統一

- **Decision**: Better Auth の `emailAndPassword` を全利用者に使う。
  - 新規登録は自前の Server Action（`signUp`）で受け、種類（求職者 `PERSON`／企業 `EMPLOYER`）を検証してから Better Auth のユーザー作成を呼ぶ
  - `requireEmailVerification: true`。確認メールのリンクを開くまで、投稿・応募・メッセージの送信はできない（閲覧とプロフィール入力はできる）
  - パスワードは8文字以上。よく使われるパスワードの一覧（上位 10,000 件程度）をリポジトリに持ち、該当すれば拒否する
  - パスワードの再設定は Better Auth の `sendResetPassword`（メールのリンク、有効期限1時間）
  - 誤入力の制限：同じアカウントで15分以内に10回失敗したら15分ロックし、本人にメールで知らせる（Better Auth のフックで失敗回数を数える）
  - 001 の `magicLink` と `twoFactor` プラグインは設定から外す。`two_factors` テーブルは将来の多要素認証のために残す
- **Rationale**: 仕様（FR-001〜FR-007）と原則VIII。種類の決定を自前で行うことで、利用者が運営（`STAFF`）を名乗る経路をなくす。
  漏えいパスワードの照合に外部サービス（Have I Been Pwned など）を使わないのは、外部依存とパスワード由来の情報の送信を避けるため。
- **Alternatives considered**:
  - Better Auth の `additionalFields` で種類を登録時に受け取る：入力値の検証を誤ると権限昇格につながるため不採用
  - Have I Been Pwned プラグイン：照合精度は高いが外部依存。必要になれば後から追加できる
- **将来の多要素認証**: Better Auth の `twoFactor`（TOTP）またはパスキーのプラグインを追加する。既存の利用者は任意で設定する形にし、ログインできなくならないようにする（原則VIII）

## R2. メッセージを「数秒以内」に届ける方法

- **Decision**: 会話画面を開いている間、3秒ごとに「最後に受け取ったメッセージより後」だけを取りにいく（差分のポーリング）。
  画面が非表示（別タブなど）のときは間隔を30秒に延ばす。
- **Rationale**: SC-005（95% が5秒以内）を満たし、ECS のタスクが複数になってもタスク間の連携が要らない。
  サーバー側の常時接続や配信の仕組みを持たずに済み、保守が最も楽。
- **Alternatives considered**:
  - Server-Sent Events + PostgreSQL の LISTEN/NOTIFY：通信量は減るが、接続の管理・ALB のタイムアウト・タスク間の通知が必要
  - WebSocket（API Gateway や外部サービス）：構成要素が増える。利用者が増えて通信量が問題になったら検討する

## R3. バックグラウンド処理（メール通知・掲載期限・新着求人の通知）

- **Decision**: **pg-boss**（PostgreSQL をキューとして使うジョブ管理ライブラリ）を使い、Next.js の `instrumentation.ts` の `register()` でワーカーを起動する。
  | ジョブ | タイミング | 内容 |
  |--------|------------|------|
  | `message-digest` | メッセージ送信の5分後 | まだ読まれていなければ、受信者に新着をメールで知らせる（同じ会話は30分に1回まで） |
  | `job-expiry` | 毎時 | 掲載期限を過ぎた求人を掲載終了にする |
  | `job-alert` | 毎朝8時 | 保存した検索条件に合う新着求人をまとめてメールで知らせる |
  | `job-change-notice` | 求人の労働条件の変更時 | 応募者に変更を知らせる（会話にシステムメッセージ＋メール） |
  | `report-sla` | 毎朝9時 | 受付から1営業日を過ぎた未対応の通報・お問い合わせを運営に知らせる |
- **Rationale**: 追加のインフラ（SQS・EventBridge・別のワーカーサービス）なしで、複数タスクでも二重実行しない仕組みが手に入る。
  ジョブの状態が DB に残るため、失敗の再実行や確認がしやすい。
- **Alternatives considered**: Amazon SQS + EventBridge Scheduler + 別の ECS タスク（堅いが構成要素が増える）、`setInterval`（複数タスクで二重実行される）

## R4. 求人の検索（日本語）

- **Decision**: 絞り込み（職種・勤務地・雇用形態・給与）は通常のインデックスで、キーワードは PostgreSQL の `pg_trgm` 拡張（3文字単位の部分一致インデックス）と `ILIKE` で検索する。
  対象はタイトル・業務内容・企業名。
- **Rationale**: PostgreSQL の標準の全文検索は日本語の単語分割ができない。`pg_trgm` は RDS で使え、公開後しばらくの規模（数千〜数万件）なら十分速い。
- **Alternatives considered**: `pg_bigm`（日本語により向くが、RDS での利用可否とバージョンの確認が要る）、Amazon OpenSearch（規模が大きくなったら検討）

## R5. 求人の掲載ルール（法令対応）の実装方針

- **Decision**: 求人の入力ルールを1か所（`src/server/compliance/`）に集め、画面の入力チェック・サーバーの検証・テストで同じ定義を使う。詳細は [contracts/compliance-rules.md](./contracts/compliance-rules.md)。
  - 必須の労働条件（FR-009）は Zod のスキーマで表し、1つでも欠けたら公開できない
  - 性別を限定する表現は、語句の一覧で検出して公開を止める（例：「女性のみ」「男性限定」「女性歓迎」）
  - 年齢の条件は、法令の例外理由（労働施策総合推進法施行規則の例外事由）を選んだときだけ入力できる
  - 求人を公開・更新するたびに、その時点の内容を履歴（版）として保存する。応募者がいる求人の労働条件が変わったら通知する
- **Rationale**: 法令対応のルールが画面ごとにばらつくと、抜け漏れがそのまま法令違反になる。1か所の定義とテストで守る。
- **注意**: 語句の一覧による検出は完全ではない。通報と運営の見回りで補う（spec の「掲載の審査」）。語句の一覧は公開前に専門家の確認を受ける。

## R6. メッセージの通信の秘密

- **Decision**:
  - メッセージ本文は、アプリケーション側で暗号化して保存する（AES-256-GCM。鍵は Secrets Manager、ローカルは `.env.local`）。鍵の世代を本文に付け、鍵の入れ替えに対応する
  - 運営の画面・権限の定義（policy）に、会話・メッセージを読む操作を作らない
  - 通報のとき、通報者が選んだメッセージだけを、通報の「提出物」として平文で複製する（通報者の同意に基づく提出）
  - システムが送るお知らせ（「応募しました」「労働条件が変更されました」）は、利用者の本文とは別の種類のメッセージとして保存する（利用者の本文は加工しない）
- **Rationale**: 電気通信事業法の通信の秘密（原則VII）と、職業紹介に当たらないための「意思疎通の内容を加工しない」（指針 第五の六(二)ハ）を、データの持ち方で保証する。
  DB を直接見られる立場の人でも、鍵なしでは本文を読めない。
- **Alternatives considered**: 暗号化なし（運営画面で見せないだけ）：DB を直接見れば読めてしまう。エンドツーエンド暗号化：通報の仕組み・データの持ち出しが難しくなり、初期には過剰

## R7. 回数制限（スパム対策）

- **Decision**: 求人の公開・メッセージ・応募の回数は、DB の件数で数える（例：メッセージは1アカウント10分で30件、新しい会話は1日20件、求人の新規公開は1日10件）。
  超えたら送信を止め、操作履歴に記録して運営の画面に表示する。
- **Rationale**: 001 のメモリ上の制限はタスクごとで、タスク数が増えると不正確になる。DB の件数なら正確で、追加のインフラも要らない。

## R8. 人を集めるための工夫（検索エンジン・共有）

- **Decision**:
  - 求人の詳細ページはサーバーで描画し、タイトル・説明などのメタ情報を設定する
  - Google の求人検索に載るよう、求人ページに構造化データ（`JobPosting`）を埋め込む。掲載終了した求人では外す
  - SNS で共有したときのカード表示（OGP）を設定する
  - サイトマップを出力する
- **Rationale**: 「流布して人を集める」ための、費用のかからない集客の土台。

## R9. デザインの方向性

- **Decision**: 「気軽に、あかるく、まっすぐ」をコンセプトに、掲示板に貼られた付箋のようなカードを基調にしたポップなデザインにする。
  丸ゴシック体（Zen Maru Gothic）、黄色を主色、ふち取りの太線と少しずらした影で楽しさを出しつつ、文字と背景のコントラストは WCAG AA を守る。
  詳細は [contracts/design-system.md](./contracts/design-system.md)。
- **Rationale**: 原則VIII と FR-047〜FR-050。白い背景に青いボタンの「よくある求人サイト」と見分けがつき、気軽さが伝わる。
- **Alternatives considered**: 落ち着いたビジネス向けの配色（信頼感は出るが、気軽さが伝わりにくい）

## R10. 001 の実装の扱い

- **Decision**:
  - 本人（求職者）向けの Axis の画面（節目・対話・整理結果・共有）は `/axis` 以下に移し、追加機能の利用権（`AXIS_ENGINE`）がある人だけが使えるようにする
  - 人材紹介会社向けの画面（`/agency/*`）と運営の旧画面は、環境変数 `ENABLE_AGENCY_PILOT`（既定は `false`）で無効にし、掲示板の画面からはリンクしない。コードとデータは残す
  - `/login` はメールアドレス＋パスワードの共通のログイン画面に置き換える。`/agency/login` と `/agency/security` は `/login` に転送する
  - DB のテーブルは残す。新しいテーブルを追加し、`UserKind` に `EMPLOYER` を加える
- **Rationale**: 001 の成果（対話・整理結果）を Axis エンジンとして活かしつつ、掲示板の画面を簡潔に保つ。データを消さないので、後から人材紹介会社向けを再開できる。

## R11. 追加機能の利用権

- **Decision**: `FeatureEntitlement` テーブル（利用者・機能・開始日・終了日・付与の経路）で管理する。当面は運営が画面から手動で付与する。
  決済との連携（付与の経路 `SUBSCRIPTION`）は、料金の受け取り方が決まってから別の仕様で作る。
- **Rationale**: 料金が未決でも、利用権の仕組みだけ先に作っておけば、決済の追加は「利用権を付ける処理」を足すだけで済む。

## R12. 運営の画面と権限

- **Decision**: 運営（`STAFF` かつ `isOperator`）の画面を `/ops` 以下に置く。できること：通報の確認と対応、求人の修正依頼・非公開化、アカウントの停止、お問い合わせの対応、利用権の付与、事業概況報告用の集計。
  運営の操作はすべて操作履歴に残す。運営アカウントは当面、シードやコマンドで作る（画面からの登録はできない）。
- **Rationale**: 指針が求める苦情処理の体制と、不適切な求人への対応（原則VII）。

## R13. 利用規約・プライバシーポリシー・事業者情報

- **Decision**: `/terms`（利用規約）、`/privacy`（プライバシーポリシー）、`/company`（運営者情報・届出の情報）、`/contact`（お問い合わせ）を用意する。
  規約の版を持ち、登録時に同意した版と日時を記録する。文面は専門家の確認を受けたものに差し替える前提で、仮の文面を置く。
- **Rationale**: FR-046 と、届出・苦情窓口の明示（原則VII）。
