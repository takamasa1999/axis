# Research: Phase1 本人起点のキャリア対話と許可制共有

**Date**: 2026-10-03 | **Plan**: [plan.md](./plan.md)

前提条件（ユーザー指定）: 本番環境は AWS、検証環境はローカル、実装は Next.js など汎用的でメンテナンスが楽なもの。
選定の基準は「3名の創業チームで保守できること」「ローカルと本番の差を小さくすること」
「Constitution（特に原則IV・V：許可制共有と本人所有）を構造で守れること」の3つ。

---

## R1. アプリケーション構成

- **Decision**: Next.js（App Router）+ TypeScript の**単一のフルスタックアプリ**とする。画面・サーバー処理（Server Actions / Route Handlers）・
  バッチ処理を1つのリポジトリ・1つのデプロイ単位にまとめる。
- **Rationale**: 利用者は Phase1 全体で数十〜数百名と小さく、API サーバーとフロントを分けるメリットがない。
  言語を TypeScript に統一すると、画面・サーバー・インフラ定義（CDK）・テストを同じ言語で書ける。
- **Alternatives considered**:
  - フロント（Next.js）＋ API（NestJS / FastAPI）の分離：デプロイ単位と言語が増え、3名では保守負荷が大きい
  - Remix / Nuxt：採用実績と情報量で Next.js を優先

## R2. 実行環境（AWS 本番）

- **Decision**: **ECS on Fargate + ALB** で Next.js をコンテナ実行する。Next.js の `output: "standalone"` で
  Docker イメージを作り、同じイメージをローカルでも動かせるようにする。
- **Rationale**: ローカル（Docker）と本番でまったく同じものを動かせるため、「ローカルでは動くのに本番で動かない」が起きにくい。
  AI の応答をストリーミングで返す長めのリクエストやバックグラウンド処理も、実行時間の制限を気にせず扱える。
  Next.js の新機能を待たずに使える（ホスティング側の対応待ちがない）。
- **Alternatives considered**:
  - AWS Amplify Hosting：最も手軽だが、Next.js の新バージョンへの対応待ちが起きやすく、VPC 内の RDS への接続やストリーミングの制約を確認する手間がある
  - Lambda + OpenNext / SST：費用は安いが、構成要素が多く、不具合を調べるのが難しい
  - App Runner：新規の機能追加が少なく、長期の保守を考えて見送る
- **費用の目安**（東京リージョン、最小構成）: Fargate 1タスク + ALB + RDS 最小インスタンスで月 1〜2万円程度。共同検証の規模なら十分。

## R3. データベース

- **Decision**: **PostgreSQL**（本番：Amazon RDS for PostgreSQL、ローカル：Docker の postgres）。ORM は **Prisma**。
- **Rationale**: 本人・節目・対話・共有許可・操作履歴の関係がはっきりしたデータで、リレーショナルデータベースが合う。
  Prisma は型付きのクエリとマイグレーション管理が一体で、利用者が多く情報も多い。
  記録項目の追加（spec FR-010 の⑥〜⑧）は、種別を表す列の値を増やすだけで済む形にする。
- **Alternatives considered**:
  - DynamoDB：関係の多いデータと集計（FR-029）に向かず、ローカルとの差も大きい
  - Aurora Serverless v2：アクセスが少ない時期には割高になりうる。規模が大きくなってから移行を検討する
  - Drizzle：軽量だが、マイグレーション運用の分かりやすさで Prisma を優先

## R4. 認証・権限

- **Decision**: **Better Auth**（Next.js 内で動く、データを自分の PostgreSQL に保存する認証ライブラリ）を使う。
  - 本人：**メールのマジックリンク**（パスワードなし）。本人のアカウントは紹介会社から独立させる（spec Assumptions）
  - CA・紹介会社管理者・運営：メール＋パスワード、および二要素認証（TOTP）を必須とする
  - 権限の判定は `src/server/policy/` の1か所に集め、すべての読み取り・書き込みがそこを通る
- **Rationale**: ローカルでも本番でも同じ認証の仕組みで動かせる（外部の認証サービスに依存しない）。
  本人が機微な記録を持つため、CA 側は二要素認証で守る。
- **Alternatives considered**:
  - Amazon Cognito：AWS 本番では自然だが、ローカルで再現しにくく、画面のカスタマイズに手間がかかる
  - Auth.js（NextAuth）：現在は Better Auth 側が保守を引き継いでおり、新規なら Better Auth を選ぶ
- **メール送信**: 本番は Amazon SES、ローカルは Mailpit（届いたメールをブラウザで確認できる開発用ツール）。

## R5. AI 対話

- **Decision**:
  - LLM は **Claude**。本番は **Amazon Bedrock** 経由で呼ぶ（対話データが AWS の外に出ない）。ローカルは Anthropic API または Bedrock、テストではモックを使う。
  - 呼び出しは **Vercel AI SDK** を使い、プロバイダー（Bedrock / Anthropic / モック）を環境変数で切り替える。
  - 対話用のモデルは Claude Sonnet 系、整理結果の作成も同じモデルから始める。モデル ID は環境変数で管理し、コードに直接書かない。
- **Constitution 原則II（AIは答えを決めない）を守る仕組み**:
  1. システムプロンプトで、応答を「問い」と「考える材料」に限ることを指示する
  2. 応答を構造化して受け取る（`kind: "question" | "material" | "safety"`）。それ以外の形の応答は再生成する
  3. **評価用のテストセット**（「転職すべき？」「決めて」などの誘導質問）を用意し、プロンプトやモデルを変えるたびに自動で評価する（CI で実行）
  4. 危険な兆候（強い心理的負担）を検知したら、対話を止めて相談窓口を案内する定型の応答に切り替える（FR-009）
- **Rationale**: Bedrock を使うと、データの扱いを AWS との契約の範囲内に収められる。AI SDK はストリーミング表示と
  プロバイダーの切り替えを最小限のコードで実現できる。
- **Alternatives considered**:
  - Anthropic API を本番でも直接呼ぶ：手軽だが、データの保管場所と契約の説明が2系統になる
  - LangChain：Phase1 の対話（1本の会話＋要約）には大きすぎる

## R6. 共有の仕組み（原則IV・V を構造で守る）

- **Decision**: 共有は**許可した時点の内容をコピーして保存する（スナップショット）**方式にする。CA はスナップショットだけを読み、
  本人の元の記録（対話の全文・整理結果）を読む経路をそもそも作らない。
- **Rationale**: 「再許可するまで前回許可した版だけを見せる」（FR-021）、「対話の全文は見せない」（FR-024）を、
  権限チェックの書き忘れに頼らず、データの持ち方そのもので保証できる。
- **取り消し・関係終了**: スナップショットに `revokedAt` / 関係に `endedAt` を記録し、CA 側の読み取り時に必ず確認する。
- **本人による削除**: 本人が記録を削除すると、Axis 上のスナップショットも削除する。紹介会社が自社システムへ転記済みの内容は
  その会社の範囲で扱われる旨を、削除の前に本人に示す（FR-032）。

## R7. 既存システムとの連携（CA 向け）

- **Decision**: 許可済み要約の「コピーボタン（整形済みテキスト）」と「CSV ダウンロード」だけを提供する。API 連携は作らない。
- **Rationale**: 資料の方針「CSV・コピーしやすい形式から始め、連携は最小限」（反論④の対策）に従う。

## R8. ローカル検証環境

- **Decision**: `docker compose` で PostgreSQL と Mailpit を起動し、アプリは `npm run dev` で動かす。
  本番と同じ Docker イメージをローカルで動かす確認手順も用意する。AI はモック（固定の応答）でも一通り動くようにする。
- **Rationale**: 新しいメンバーが `docker compose up` と `npm run dev` だけで始められる。API キーがなくても画面の確認ができる。

## R9. インフラ定義・デプロイ

- **Decision**: **AWS CDK（TypeScript）** で `infra/` に定義する。GitHub Actions から、`main` へのマージで
  テスト → イメージのビルド → ECR へのプッシュ → ECS の更新、の順に自動で実行する。AWS への認証は OIDC を使う（アクセスキーを保管しない）。
- **Rationale**: アプリと同じ TypeScript で書ける。Terraform より学ぶことが少ない。
- **Alternatives considered**: Terraform（汎用的だが言語が増える）、SST（便利だが構成が独自で、隠れる部分が多い）

## R10. 品質管理ツール

- **Decision**:
  - 単体・結合テスト：**Vitest**（結合テストはローカルの PostgreSQL を使う）
  - E2E テスト：**Playwright**（本人の対話〜許可〜CA の閲覧までを通しで確認）
  - リンター・フォーマッター：**Biome**（1つのツールで両方を担う）
  - 入力チェック：**Zod**（フォームの入力、AI の構造化出力、CSV の行を同じ定義で検証）
  - UI：**Tailwind CSS + shadcn/ui**（部品のコードを自分のリポジトリに持つため、外部ライブラリの破壊的変更の影響を受けにくい）
- **Rationale**: ツールの数を最小にし、利用者の多い定番を選ぶ。

## R11. セキュリティ・個人情報

- **Decision**:
  - 保存時の暗号化（RDS・S3 は KMS で暗号化）、通信は TLS のみ
  - データベースは非公開のサブネットに置き、アプリからだけ接続できるようにする
  - 秘密情報（DB 接続、API キー、認証の鍵）は AWS Secrets Manager で管理する
  - 操作履歴（共有・許可・修正・取り消し・閲覧・出力）は追記のみのテーブルに残す（FR-022）
  - アプリのログに対話本文を出さない（ログに個人の内容を残さない）
  - 東京リージョン（ap-northeast-1）に置く
- **Rationale**: Constitution「プライバシー・データ取扱い要件」と、検証段階の小さなチームでも守れる最低限の対策。
  法務・セキュリティの詳細な確認は、資料 STEP7（小規模な資金調達）の使途に含まれる。
