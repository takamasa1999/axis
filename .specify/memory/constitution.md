# Axis Constitution

## Core Principles

### I. 本人主体（Person-Centered）

- キャリア形成の主体は常に本人である。すべての機能は「本人にとっての価値」を最初に評価する。
- 本人に価値がない機能は、CA・人材紹介会社にとって価値があっても採用しない
  （価値の検証順序は「本人 → CA → 紹介会社」）。
- Phase1で人材紹介市場を使う場合も、プロダクトは「人材紹介向け業務効率化ツール」ではなく、
  本人のAxisを始める最初の入口として設計する。

**Rationale**: 本人に価値がなければ、CA・紹介会社への価値も成立しない（資料 p.17）。

### II. AIは答えを決めない（No Answers, Only Material & Questions）

- AIの出力は「考える材料（過去の判断軸との比較など）」と「問い（見落としている観点など）」の
  2種類に限る。
- AIは本人の代わりに選ばない。転職すべきかを判定しない。正解を1つに絞って示さない。
- 「今は転職しない」も、深く考えた結果として正しい選択肢の1つとして扱う。
  転職・応募へ誘導する表現や設計は禁止する。

**Rationale**: 答えを持つのは本人であり、Axisは本人が自分で選べる状態をつくる（資料 p.7, 22）。

### III. 判断の過程を時間軸で蓄積する（Longitudinal Decision History）

- Axisの中心は経歴（結果）ではなく「どう考え、どう変わったか」の記録である。
- 記録は節目（就職・転職・昇進/異動・学び直し・人生の変化）ごとに時点付きで残し、
  後から過去の自分の判断と比較できなければならない。
- 利用頻度（毎日使われること）を成功指標にしない。節目に「戻ってくる場所」であることを目指す。

**Rationale**: 履歴書には「なぜ選んだか」が残らず、自己分析が毎回ゼロからになる（資料 p.4, 6, 8）。

### IV. 共有は本人の確認と許可が前提（Consent-Gated Sharing）

- 本人の記録を第三者（CA・人材紹介会社・学校・勤務先など）へ渡すときは、
  本人が内容を確認・修正し、共有範囲を選び、明示的に許可した後に限る。
- 共有の可否を決める主体は常に本人である。既定値は「共有しない」とする。
- 第三者に渡すのは本人が許可した範囲のみ。対話の全文など、許可されていない情報は渡さない。

**Rationale**: 「本人が確認・許可した内容だけが、CA面談の前に届く」（資料 p.16, 18）。

### V. 本人のAxisは本人に残る（Person-Owned Data, No Lock-in）

- 支援者（紹介会社・学校・勤務先）との関係が終わっても、本人のAxisは本人に残り続ける。
- 第三者へ共有済みの情報は、その第三者の範囲で扱われる。本人側の記録は削除・縮退しない。
- Axisは人材紹介会社の求職者データベースになることを目的にしない。
  データの囲い込みを競争優位にしない。データを本人の同意なく企業資産化しない。

**Rationale**: 支援者が変わっても履歴が途切れないことが、Phase2〜4の土台になる（資料 p.9, 10, 18）。

### VI. 利益のために本人主体を壊さない（Integrity over Revenue）

- 利益は事業継続の条件だが、本人の主体性を損なう利益であれば、その事業・機能は選ばない。
- 費用負担者（紹介会社）の要望が原則I〜Vと衝突する場合、原則を優先する。
- 両立できないと分かった市場には固執しない（撤退・見直し基準に従う）。

**Rationale**: 成功報酬モデルと「今は転職しない」の正しさは衝突しうる（資料 p.22）。

## プライバシー・データ取扱い要件

- 個人のキャリア対話は機微情報として扱う。収集は検証・提供価値に必要な最小限とする。
- 研究・統計利用（Phase4構想）は、本人同意と匿名化を前提とする。同意のない二次利用は行わない。
- 本人は自分の記録をいつでも閲覧・修正・削除・持ち出しできなければならない。
- 共有・許可・取り消しの操作は、後から本人が確認できる形で記録する。
- 求職者本人からは料金を取らない構造で検証する（Phase1）。

## 検証駆動の開発プロセス

- 仕様・計画では、内容のステータス（方針／仮説／外部調査／仮置き／判断基準案／未決／長期構想）を
  区別して記述する。仮説や仮置きの数値を確定事項として扱わない。
- 検証（インタビュー・簡易試作・共同検証）で必要と分かった機能だけを作る。
  初期から大規模な外部システム連携は作らない（CSV・コピーしやすい形式・必要最小限の連携から始める）。
- 撤退・見直しの判断基準を、検証を始める前に数値で決める。
- 支払い意思の証拠がない段階で、大きな固定費を前提とした開発計画を立てない。

## Governance

- この Constitution は、Axis のすべての仕様（spec）・計画（plan）・タスク（tasks）・実装に優先する。
- `/speckit-plan` の Constitution Check では、原則I〜VIへの適合を必ず判定する。
  違反がある場合は、理由と代替案の検討を Complexity Tracking に記録し、創業メンバーの合意を得る。
- 改定は創業メンバー3名（Founder / Engineer / Solution Sales・AI Engineer）の合意で行い、
  改定理由と影響範囲を Sync Impact Report に記録する。
- バージョンはセマンティックバージョニングに従う。
  MAJOR：原則の削除・再定義／MINOR：原則・節の追加や大幅な拡張／PATCH：表現の明確化・誤字修正。
- 事業構想資料の改版（v0.3 以降）で「方針」が変わった場合は、この Constitution の改定要否を確認する。
